# AI task and background-agent reliability

Parent: PR #59 at `9fd27ab86dc0ae0e16e07577b17b71c6e4465c1e`. Isolated continuation branch: `codex/ai-agent-reliability-20260909`. Payment sources/configuration, user records, production deployment and previous worktrees are not changed.

## What actually executes

`AI_FEATURE_INVENTORY_20260909.json` is generated by a TypeScript AST scan of real source call sites. It names **24 executable LLM tasks** plus the separate voice-transcription adapter. Five tasks take images; the other 19 are text inputs. The task registry and consent-disclosure scope are tested against actual callers. The old unused `daily-readiness` and `workout-structure` route labels were removed, not counted as working agents. Readiness itself remains calculated by the existing deterministic engine.

The provider-neutral `AICoachWorker` interface is an extension contract, not an autonomous deployed worker. Night Lab is currently a scheduled deterministic athlete-state refresh, not a team of medical or generative agents. The inventory labels those distinctions explicitly.

## Shared model execution fixes

The JSON generator previously validated a Zod schema only after the response but did not send that schema to the model. A task without its own hand-written shape could therefore fail despite reaching a provider. Every structured request now includes the input JSON Schema alongside task instructions and is validated again with the original Zod contract. JSON Schema does not express every custom Zod refinement: local validation remains authoritative.

The parser no longer drops an incomplete final item and manufactures closing brackets. It accepts complete JSON, optionally in one complete presentation fence, while preserving string contents. Output truncated by a token limit, refused by the provider, empty, oversized, or incompatible with the response contract is rejected. An invalid recommendation does not get retried through progressively weaker validators or become a successful plan by repairing its tail.

Model construction reads the current server configuration when invoked rather than capturing an empty or older key at module import. Actual provider SDK adapters are exercised over mocked HTTP, including configuration changes. This test is not a live provider availability check.

Every task has a centrally approved fallback route. Existing explicit critical-plan routes are retained; previously single-provider tasks receive compatible backups. Image tasks never fall back to the text-only worker. Provider unavailability, timeout, rate limits or missing model configuration may use another approved provider; invalid domain output cannot. The single orchestrated route reserves quota once, not once per fallback. A voice feature still performs transcription and structuring as two separately counted operations. A null quota response is infrastructure unavailability, not proof the athlete used their daily allowance.

Requests have a 90-second orchestration deadline and 45-second per-provider deadline with abort signals. SDK retries are disabled inside each attempt so the central route owns retries. The elapsed deadline is enforced even if an adapter ignores cancellation; subsequent provider attempts check the aborted signal. These limits do not extend a hosting platform's execution time. Multi-step features (for example two recipe parts or a translation sequence) may require a larger total workflow budget or a future persisted job design before production rollout.

A prebuilt central-context object must have been created by GYMS.LIFE for the same user. A private WeakMap records its owner without adding identifiers to the provider payload. Existing explicit-consent filtering is preserved. The shared instruction makes clear that supplied records/transcripts are data, not system authority, and that workers cannot claim to have saved data. This is a defence layer, not a proof against every prompt injection or semantic error.

## Media and voice

The orchestration boundary permits bounded inline PNG/JPEG/WebP images, checks their container signatures, rejects remote URLs and unsupported parts, and bounds image count and total size. This prevents a task from silently fetching arbitrary URLs or sending an unbounded payload. It is not a full media decoder or a guarantee that a picture is meaningful.

Audio requests validate canonical base64, accepted MIME, payload size and the selected supported language. MP4 audio gets an `.m4a` filename rather than always pretending to be WebM. Transcription requests have a deadline and consistent safe error handling. All eight product locales are passed through rather than treating six of them as English.

The microphone component selects a recorder format the browser supports, releases tracks on stop/error/unmount, bounds recording duration and avoids duplicate permission/record requests. Its result is a **draft**, not a falsely logged set. Missing weight, reps, RPE and rest stay null rather than borrowing example values. The actual workout form accepts the user's reviewed draft, clears missing fields and leaves the existing explicit Log set action as the only save. The recorder is scoped to the session/exercise/set key, so moving to another set unmounts the old recording/draft rather than applying its late response there. The old unused local tracker is labelled as temporary drafts; it is not advertised as database persistence.

## Warm-up and background work

Warm-up generation now starts only on user request, not every mount/remount. The query key includes user, language and workout inputs. Concurrent refetch requests deduplicate and stale results are not painted into another input's query. Provider failures remain visible rather than being replaced with a generic fixed warm-up labelled as a personalized success. Returned exercise identifiers are restricted to the existing warm-up list; readiness is taken only from the athlete's current local day and a failed read is not treated as missing data. This does not clinically approve a drill for an injury.

An expired Night Lab claim is taken over only when the stored start timestamp still matches the one read. A previous holder cannot acknowledge completion after a newer lease replaced it. Completion requires a returned matching row; zero updated rows are not recorded success. Failed/unrecorded run outcomes become HTTP 503 to the scheduler rather than HTTP 200. Scheduler transport is bounded and failures use a stable message.

The lease fix fences claiming and final acknowledgement. It does not make every side effect globally exactly-once after a long-running lease expires. Existing per-source row bounds, partial-source handling and cross-period recovery remain review items. The task schedule was not enabled or manually run against real athletes.

## Evidence, not live guarantees

The full orchestration integration matrix executes each registered task using controlled model/HTTP responses and verifies scope, schema transmission, output parsing, quota, compatible fallback and deadlines. Separate tests cover real SDK request/response formatting, voice language and MIME contracts, malformed media, null extracted values, and background claim/close behaviour. The browser suite exercises real warm-up and workout/voice components with a synthetic recorder and synthetic server responses; no microphone permission or recording from the user was requested.

Read-only production aggregates from the preceding 14 days showed earlier AI successes and failures, including unavailable models and quota failures. Those rows belong to previously deployed code, not this patch. The background-job ledger query returned **no rows in that window**, so there is no evidence from that ledger that Night Lab ran in production recently. Provider keys and the cron secret were absent in the authoring shell process; that says nothing about the deployment environment. No environment secrets were read to invent a live acceptance result.

No new live AI request, medical/allergen certification, production job execution, schema migration, payment change, merge or deployment is part of this block. Live provider responses, actual device capture, scheduler configuration, hosting time budgets and remaining feature-specific recommendation quality must be validated separately. Prior nutrition restrictions and account-scoped offline-recovery limitations remain unchanged.
